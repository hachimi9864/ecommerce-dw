从 0 到 1 搭一个能写进简历的电商数据仓库 | 手机/电脑都能看

① 概念扫盲（建议先看，不然跑了也不知道在干啥）

🎯 这个项目到底在做什么？

一句话：把淘宝用户的点击/收藏/加购/购买记录，加工成老板能看懂的分析结论。

比如："整体转化率 24%""重要价值客户占 25.5%""晚上 8 点最活跃"——这些结论不是凭空来的，是从 50 万行原始数据一层层加工出来的。

📦 什么是数据仓库？为什么要分层？

想象你开了一家餐厅：

  • 买菜（ODS）：从菜市场买回来的原材料，带着泥，不能直接上桌
  • 洗菜切菜（DWD）：把泥洗掉，切成能用的形状，但还是生的
  • 配菜（DWS）：把要炒同一道菜的食材放一起，炒的时候直接拿
  • 炒菜装盘（ADS）：端给客人吃的成品菜

为什么不直接从原始数据炒？因为每次都从 50 万行原始数据里算，又慢又容易算错。分层后，"洗菜切菜"只做一次，后面所有菜都能复用，而且口径统一。

🧱 四层架构一图看懂

ODS 原始层→DWD 明细层→DWS 汇总层→ADS 应用层
原始日志 → 清洗去重 → 按天/人聚合 → 漏斗/RFM等分析结果
层作用本项目的表
ODS原样存原始数据，不加工ods_user_behavior（50万行）
DWD清洗+拆出日期/小时等维度，还是一行一个行为dwd_user_behavior（~50万行）
DWS按用户/商品/天聚合，行数变少dws_user_day / dws_item_day / dws_user_summary
ADS直接出分析结果，给业务看的漏斗表 / RFM分群表 / 活跃表

📖 名词大白话解释

名词大白话
UV独立访客数，去重后的人数。1万人各点1次=1万UV；1人点1万次=1UV
PV页面浏览量，点击总次数。1人点1万次=1万PV
转化漏斗用户从"看"到"买"逐步流失的过程，像漏斗一样越往下人越少
RFM衡量用户价值的三个维度：R最近买过没、F买了多少次、M花了多少钱
维度退化把"日期""小时"这种本来要算的字段，提前算好塞进表里，用的时候直接取
宽表把一个用户的所有指标（浏览数、购买数、首购日…）摊平成一行很多列
粒度表的每一行代表什么。比如"用户-日"粒度=每个用户每天一行
CTASCREATE TABLE AS SELECT 的缩写，用查询结果直接建表
索引书的目录，加了索引查特定行更快，但会占空间、拖慢写入

01_create_ods.sql 逐段解释

① 建库

CREATE DATABASE IF NOT EXISTS ecommerce_dw
DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
  • CREATE DATABASE：创建数据库（相当于建一个文件夹装表）
  • IF NOT EXISTS：如果已存在就不报错，保证脚本能重复跑
  • utf8mb4：字符集，必须用这个，才能存中文和 emoji（普通 utf8 存不了 emoji）

② 切换到这个库

USE ecommerce_dw;

告诉 MySQL 接下来的操作都在这个库里执行，不然它不知道往哪建表。

③ 删旧表（可选但推荐）

DROP TABLE IF EXISTS ods_user_behavior;

如果这张表已经存在就先删掉。为什么要删？因为 CREATE TABLE 不能建已存在的表，会报错。学习阶段数据不重要，删掉重建最干净。

④ 建 ODS 表（核心）

CREATE TABLE ods_user_behavior (
    user_id       INT          NOT NULL COMMENT '用户ID',
    item_id       INT          NOT NULL COMMENT '商品ID',
    category_id   INT          NOT NULL COMMENT '商品类目ID',
    behavior_type VARCHAR(10)  NOT NULL COMMENT 'pv浏览/fav收藏/cart加购/buy购买',
    behavior_time DATETIME     NOT NULL COMMENT '行为发生时间',
    KEY idx_user (user_id),
    KEY idx_item (item_id),
    KEY idx_time (behavior_time),
    KEY idx_type (behavior_type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='ODS层-淘宝用户行为原始表';

逐列解释：

字段类型为什么是这个类型
user_idINT用户ID是整数，INT 存 -21亿~21亿，够用
item_idINT商品ID也是整数
category_idINT类目ID
behavior_typeVARCHAR(10)行为是字符串（pv/fav/cart/buy），最长4个字符，给10足够
behavior_timeDATETIME时间，精确到秒，格式 '2017-11-25 10:30:00'

NOT NULL：这一列不允许空值，保证数据质量。

COMMENT：给字段加注释，别人看表结构时知道这列啥意思。好习惯，面试加分。

KEY idx_user (user_id)：给 user_id 加索引。为什么加？后面要按用户查数据，没索引的话 50 万行全表扫描会很慢。索引=书的目录。

ENGINE=InnoDB：MySQL 的存储引擎，支持事务和外键，默认就行。

load_data.py 核心逻辑解释

import pymysql
conn = pymysql.connect(host='localhost', user='root', password='你的密码', database='ecommerce_dw')

这三行：连上 MySQL 数据库。pymysql 就像一座桥，让 Python 能和 MySQL 说话。

TRUNCATE：清空表。保证重复跑脚本时不会重复导入。

BATCH_SIZE = 5000
for row in reader:
    batch.append(...)
    if len(batch) >= BATCH_SIZE:
        cursor.executemany(INSERT_SQL, batch)

批量插入优化：不是一行一行插，而是攒满 5000 行一次性插。为什么？一行一插要和数据库通信 50 万次，批量只需要 100 次，速度差几十倍。

Day3 · DWD 明细层（清洗 + 维度退化）

这一步在干嘛？

ODS 里的数据是"生的"——时间戳是一坨数字，要算"星期几"还得每次写函数。DWD 层把这些提前算好，变成干净好用的明细数据。

打开 sql/02_dwd.sql，全选执行。

02_dwd.sql 核心解释

建 DWD 表时多了哪些字段？

dt          DATE        -- 行为日期，如 2017-11-25
hr          TINYINT     -- 小时，0-23
weekday_cn  VARCHAR(8)  -- 星期几，中文
is_weekend  TINYINT     -- 是否周末，1是0否

这 4 个字段就是维度退化的产物——从 behavior_time 一个时间戳里拆出来的。以后查"周末的购买量"直接 WHERE is_weekend=1，不用每次写 DAYOFWEEK()。

清洗+灌入的 SQL

INSERT INTO dwd_user_behavior
SELECT
    user_id, item_id, category_id, behavior_type, behavior_time,
    DATE(behavior_time)              AS dt,          -- 截取日期部分
    HOUR(behavior_time)              AS hr,          -- 取小时
    CASE DAYOFWEEK(behavior_time)                      -- 把数字1-7转成中文星期
        WHEN 1 THEN '星期日' ...
    END                              AS weekday_cn,
    CASE WHEN DAYOFWEEK(behavior_time) IN (1,7)
         THEN 1 ELSE 0 END          AS is_weekend
FROM ods_user_behavior
WHERE behavior_type IN ('pv','fav','cart','buy')   -- 过滤非法行为
  AND behavior_time IS NOT NULL;                     -- 过滤空时间

清洗逻辑：

  • WHERE behavior_type IN (...)：只保留四种合法行为，把脏数据（比如拼错的 'pvv'）过滤掉
  • AND behavior_time IS NOT NULL：时间为空的行丢掉

加工逻辑（维度退化）：

  • DATE(behavior_time)：从 '2017-11-25 10:30:00' 取出 '2017-11-25'
  • HOUR(behavior_time)：取出 10
  • CASE WHEN ... THEN ... END：MySQL 的 if-else，把 DAYOFWEEK 返回的 1（周日）~7（周六）翻译成中文
面试话术："DWD 层主要做三件事：数据清洗（去脏去重）、字段规范化（统一命名和格式）、维度退化（把常用维度提前算好存进事实表，用空间换时间）。"

Day4 · DWS 汇总层（聚合，数据变少）

这一步在干嘛？

DWD 还是 50 万行（一行一个行为），直接在上面做分析太慢。DWS 把数据按主题聚合，行数大幅减少，后面所有分析都从这里取数。

打开 sql/03_dws.sql，全选执行。

03_dws.sql 核心解释

表1：dws_user_day（用户-日 粒度）

CREATE TABLE dws_user_day AS
SELECT
    user_id, dt,
    SUM(behavior_type = 'pv')   AS pv_cnt,    -- 当天浏览次数
    SUM(behavior_type = 'fav')  AS fav_cnt,   -- 当天收藏次数
    SUM(behavior_type = 'cart') AS cart_cnt,  -- 当天加购次数
    SUM(behavior_type = 'buy')  AS buy_cnt,   -- 当天购买次数
    COUNT(*)                    AS total_cnt  -- 当天总行为数
FROM dwd_user_behavior
GROUP BY user_id, dt;

关键技巧 SUM(behavior_type = 'pv')：

MySQL 里，条件表达式 behavior_type = 'pv' 的结果是 1（真）或 0（假）。对它求和，就等于数有多少行满足条件。等价于 SUM(CASE WHEN behavior_type='pv' THEN 1 ELSE 0 END)，但更简洁。

粒度：GROUP BY user_id, dt 表示每个用户每天一行。50万行明细 → 约 8 万行汇总（1万用户 × 9天，但不是每个用户每天都活跃）。

表3：dws_user_summary（用户生命周期宽表）

CREATE TABLE dws_user_summary AS
SELECT
    user_id,
    MIN(dt)              AS first_dt,      -- 首次活跃日
    MAX(dt)              AS last_dt,       -- 最近活跃日
    COUNT(DISTINCT dt)   AS active_days,   -- 活跃天数
    SUM(behavior_type='pv')  AS total_pv,  -- 累计浏览
    ...
    MIN(CASE WHEN behavior_type='buy' THEN dt END) AS first_buy_dt  -- 首购日
FROM dwd_user_behavior
GROUP BY user_id;

什么是宽表？把一个用户的所有指标都摊平成一行。这张表每个用户一行，后面 RFM、留存分析都直接从这取，不用再扫 50 万行。

MIN(CASE WHEN behavior_type='buy' THEN dt END)：只在购买行为里取最小日期，就是首购日。如果用户没买过，结果是 NULL。

Day5 · ADS 应用层①：转化漏斗分析

什么是转化漏斗？

电商用户的典型路径：浏览 → 收藏/加购 → 购买。每一步都会有人流失，像漏斗一样越来越窄。我们要算每一步的转化率，找出哪里流失最严重。

打开 sql/04_ads_funnel.sql，全选执行。

04_ads_funnel.sql 核心解释

CREATE TABLE ads_funnel_overall AS
SELECT
    COUNT(DISTINCT CASE WHEN behavior_type='pv' THEN user_id END) AS uv_pv,
    COUNT(DISTINCT CASE WHEN behavior_type IN ('fav','cart') THEN user_id END) AS uv_fav_cart,
    COUNT(DISTINCT CASE WHEN behavior_type='buy' THEN user_id END) AS uv_buy
FROM dwd_user_behavior;

🔑 为什么用 COUNT(DISTINCT ...)？

COUNT(DISTINCT user_id) = 去重后的用户数 = UV。

如果用 COUNT(*)，那是行为次数（PV）。一个用户刷 100 次页面，PV 会虚高 100 倍。业务关心的是"多少人"完成了转化，所以必须用 UV。

🔑 为什么把 fav 和 cart 合并？

收藏和加购都是"有购买意向"的行为。很多用户只收藏不加购，或只加购不收藏，拆开看会漏掉一批意向用户。合并后更贴近"意向漏斗"的本意。

面试加分：主动说"我也可以拆成 pv→fav→cart→buy 四级漏斗，看业务需要哪种口径"。

转化率怎么算？

uv_fav_cart * 10000 / uv_pv / 100  AS 浏览到加购转化率

先 ×10000 再 ÷100，等价于 ×100，但避免了浮点精度问题（直接 ×100 可能出现 23.99999999 这种脏数）。

Day6 · ADS 应用层②：RFM 用户价值分层

RFM 是什么？

衡量用户价值的三个维度：

字母含义怎么算越大越好？
Recency最近一次购买距今多少天参照日 - 最后购买日越小越好（最近买过）
Frequency购买频次统计周期内购买次数越大越好
Monetary消费金额累计消费金额越大越好
本项目没有 M：数据集只有行为没有金额，所以只做 R+F 二维分层。面试时主动说这个数据局限，比假装算了 M 强 100 倍。

05_ads_rfm.sql 分步解释

第一步：定参照日

SET @ref_date = (
    SELECT DATE_ADD(MAX(behavior_time), INTERVAL 1 DAY)
    FROM dwd_user_behavior WHERE behavior_type = 'buy'
);

为什么不用今天的日期？数据是 2017 年的，用今天算 R，所有人都是 3000+ 天，全错。参照日要取数据集最后一天的次日，回到业务当时的语境。

第二步：算每个用户的 R 和 F

CREATE TABLE ads_rfm_detail AS
SELECT
    user_id,
    DATEDIFF(@ref_date, MAX(CASE WHEN behavior_type='buy' THEN behavior_time END)) AS recency,
    COUNT(CASE WHEN behavior_type='buy' THEN 1 END) AS frequency
FROM dwd_user_behavior
GROUP BY user_id
HAVING frequency > 0;
  • DATEDIFF(a, b)：算两个日期差几天。参照日 - 最后购买日 = 距今天数
  • HAVING frequency > 0：只给买过的用户分层。没买过的用户属于另一类（潜在用户），不在 RFM 范围内

第三步：用 NTILE(5) 打分

6 - NTILE(5) OVER (ORDER BY recency)   AS r_score,
NTILE(5)     OVER (ORDER BY frequency) AS f_score

NTILE(5)：窗口函数，把排序后的数据尽量平均分成 5 组，每组给 1~5 的编号。

ORDER BY recency（R 升序，最近的在前）：NTILE 给第 1 组（最近的）编号 1，但最近的应该得高分 5，所以用 6 - 编号 翻转一下。

ORDER BY frequency（F 升序，最少的在前）：编号 5 就是买得最多的，直接用。

第四步：分群

CASE
    WHEN r_score >= 4 AND f_score >= 4 THEN '重要价值客户'  -- R高+F高
    WHEN r_score >= 4 AND f_score <  4 THEN '重要发展客户'  -- R高+F低（最近活跃但买得少）
    WHEN r_score <  4 AND f_score >= 4 THEN '重要保持客户'  -- R低+F高（曾经高频但很久没来了）
    ELSE '一般挽留客户'
END AS segment

分群逻辑和运营策略：

分群特征运营策略
重要价值客户最近常来+买得多VIP权益、新品首发、专属客服
重要发展客户最近常来但买得少发优惠券、凑单满减，提升购买频次
重要保持客户曾经高频但很久没来召回推送、老客专享价
一般挽留客户不来也不买低成本触达（短信/邮件），不投入太多

Day7 · ADS 应用层③：活跃分布 + 复购率

这一步在干嘛？

补充两个电商常用分析：每小时活跃分布（看什么时间人最多）、复购率（买过的人里有多少会再买）。

打开 sql/06_ads_other.sql，全选执行。

核心 SQL 解释

24小时活跃分布

SELECT hr, COUNT(*) AS pv_total, COUNT(DISTINCT user_id) AS uv
FROM dwd_user_behavior
WHERE behavior_type = 'pv'
GROUP BY hr
ORDER BY hr;

按小时分组，看每个小时的浏览 UV。真实数据应该是晚 8-10 点高峰，运营可以在高峰时段推送活动。

整体复购率

WITH buy_user AS (
    SELECT user_id, COUNT(*) AS buy_times
    FROM dwd_user_behavior WHERE behavior_type='buy'
    GROUP BY user_id
)
SELECT
    COUNT(*) AS 购买用户数,
    SUM(CASE WHEN buy_times >= 2 THEN 1 ELSE 0 END) AS 复购用户数,
    ROUND(SUM(CASE WHEN buy_times >= 2 THEN 1 ELSE 0 END) * 100 / COUNT(*), 2) AS 复购率pct
FROM buy_user;

复购率 = 购买 ≥2 次的用户数 / 买过的用户数。这是电商健康度的核心指标——拉新成本高，复购才是利润来源。

WITH ... AS：CTE（公共表表达式），把子查询起个名字复用，代码更清晰。

高频面试问题 + 标准答案

Q1：为什么要做数仓分层？

A：① 解耦，底层数据变了不影响上层分析；② 复用，DWS 层建一次所有分析都能用，不用每次扫原始数据；③ 口径统一，大家从同一张汇总表取数，不会各算各的；④ 出问题能沿血缘定位是哪一层的错。

Q2：ODS 和 DWD 的区别？

A：ODS 是原始数据原样落地，不做加工，可能有脏数据；DWD 是清洗后的明细层，做了去脏、去重、维度退化，粒度不变（还是一行一个行为），但更干净好用。

Q3：DWD 和 DWS 的区别？

A：DWD 是明细层，一行一个行为，50 万行；DWS 是汇总层，按用户/商品/天聚合，行数少很多。DWD 做清洗不做聚合，DWS 做聚合。

Q4：为什么转化率用 UV 不用 PV？

A：业务关心"多少人"完成转化。如果用 PV，一个用户刷 100 次页面会把浏览量放大 100 倍，转化率会被严重低估。UV 去重后才反映真实的用户转化。

Q5：RFM 没有 M 怎么办？

A：主动说明数据局限。如果有订单金额表，可以 LEFT JOIN 进来取 SUM(amount) 补齐 M；没有金额时，R+F 二维分层是业内常见折中。不要假装算了 M。

Q6：NTILE(5) 是什么？

A：窗口函数，把排序后的数据尽量均分成 5 组，每组编号 1-5。如果行数不能整除，前面的组会多 1 行。数据量特别小或有大量并列值时，可能切分不均匀，可以改用 CASE WHEN 自定义阈值。

Q7：你这个项目用了 Hive/Spark 吗？

A：没有。50 万行数据 MySQL 单机就够了，Hadoop/Spark 是解决 TB/PB 级数据的。我用 MySQL 实现了完整的 ODS-DWD-DWS-ADS 分层建模，HiveQL 和 MySQL 语法高度相似，数据规模上来后迁移成本很低。（然后把之前背的 Hive/Spark 概念说一下）

❌ 常见报错排查

1. Unknown database 'ecommerce_dw'

原因：还没建库。解决：先在 DBeaver 执行 01_create_ods.sql。

2. Access denied for user 'root'

原因：密码不对。解决：检查 load_data.py 第 28 行和 visualization.py 第 25 行的密码，改成你自己的。

3. UnicodeEncodeError: 'latin-1' codec can't encode

原因：密码还是中文占位符 '改成你的MySQL密码'。解决：改成你的真实密码。

4. Table 'ecommerce_dw.ads_xxx' doesn't exist

原因：漏跑了某个 SQL 脚本。解决：检查 sql 文件夹 01-06 是不是都执行过了。

5. can't open file 'scripts/visualization.py'

原因：当前目录不对。解决：先 cd C:\Users\wut98\Desktop\ecommerce-dw 再跑。

6. 左边看不到新建的表

原因：DBeaver 没刷新。解决：右键"数据库"→ 刷新，或按 F5。
